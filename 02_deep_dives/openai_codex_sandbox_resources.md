# Codex 沙箱资源限额的基本机制

> 访问权限管“程序能碰什么”，资源限额管“程序能用多少”。程序没有越权，也可能因为占用太多资源，让电脑变慢、卡住或耗尽磁盘。
>
> 核验日期：2026-10-20。Codex 源码依据提交 `091008729d5572712ac08964a9602eb71cf31428`，主要核对本地命令执行、统一终端执行器及 Linux 沙箱相关路径。本文区分操作系统提供的能力与本次源码中确认的实现；例子是教学假设，未进行资源耗尽实验。

本文是 [[openai_codex_sandbox|Codex 沙箱机制]] 的资源限额专题。先理解基本机制，具体平台与部署环境的配额留待后续核验。

## 1 为什么限制访问权限还不够

假设用户让 Codex 处理项目中的一批图片。即使程序只读写项目目录、不联网，它仍可能：

| 程序的行为 | 可能带来的问题 | 需要管什么 |
| --- | --- | --- |
| 一直做图片计算 | 其他程序变慢 | CPU 用量 |
| 一次把所有大图装进内存 | 内存紧张，程序被终止 | 内存用量 |
| 不断启动图片处理助手 | 进程或线程过多 | 任务数量 |
| 在允许写入的目录生成大量文件 | 磁盘被写满 | 磁盘用量 |
| 卡在循环里不结束 | 任务一直占着执行资源 | 运行时间 |
| 不停打印日志 | 执行器保存的输出越来越多 | 输出缓冲大小 |

**允许写入项目目录，不等于只允许写入一定大小的文件；允许启动子进程，也不等于只能启动几个。**这些需要各自的限制机制。

## 2 操作系统怎样限制 CPU、内存和任务数量

Linux 提供 **cgroups（控制组）**，可以把一组进程放在同一本“资源账本”里，由内核统计用量、执行限制。

可以把图片处理任务想成一个工作小组：主脚本和它启动的助手一起计算用量。这样可以避免只限制主脚本，助手却在旁边大量消耗资源。

这里介绍的是 Linux 的能力，**不能据此认定 Codex 已经为每条本地命令配置了控制组配额**。

### 2.1 CPU：一段时间里，最多分到多少计算机会

CPU 是实际执行计算的处理器。CPU 配额可以理解成“每一轮能领到多少计算时间”。

假设一组任务每 100 毫秒最多获得 50 毫秒的 CPU 执行时间。用完后，内核可以让这组任务等到下一轮再继续。这种处理叫**节流**，大白话就是“先歇一会儿，把计算机会让给别人”，不一定直接杀掉程序。

还要区分两个时间：

- **现实经过时间**：从开始到现在，钟表走了多久，也叫墙钟时间。
- **CPU 时间**：处理器实际为任务做了多久计算。

例如，程序等网络响应一分钟，现实过去一分钟，CPU 可能只忙了一小会儿；多个线程在多个核心上同时计算时，累计 CPU 时间又可能大于现实经过时间。

因此，**“最多运行一分钟”不能直接等价成“最多使用一分钟 CPU”**。

### 2.2 内存：这一组任务总共能占多少空间

内存是程序运行时存放数据的地方。图片处理脚本和它的助手都可能占用内存，因此限制通常需要关注整组任务的相关用量。

假设给工作小组设定 2 GB 内存上限。当用量接近或达到限制时，内核会尝试回收可回收的内存；如果无法满足新的申请，可能进入内存不足处理，导致分配失败或进程被终止。

**OOM** 是 *Out Of Memory*，就是“内存不够了”。它不是“程序申请提权后就能继续”的同一种问题。

### 2.3 任务数量：最多能有多少个执行成员

脚本可能启动子进程，子进程也可能再启动助手。Linux 的控制组任务数量限制可以阻止继续创建任务；这里的计数还涉及线程，不能只按几个脚本文件来数。

这与 [[openai_codex_sandbox_processes|进程隔离与权限边界]] 中的 PID 命名空间不同：

- PID 命名空间主要改变进程的编号和可见范围，像一本独立的通讯录。
- 任务数量限制规定这组任务最多能有多少成员，像人数上限。

**通讯录独立，不代表人数自动有限。**

一手依据：[Linux 内核 cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)中的 `cpu.max`、`memory.max` 和 `pids.max`。这些分别提供 CPU 带宽、内存和任务数量控制；具体配置、计数与处理方式以相应内核机制为准。

## 3 Codex 中，等待输出和执行超时是两回事

工具执行命令时，可能需要先等一会儿，收集输出，再把结果返回给模型。**这次等多久，不一定就是程序最多能活多久。**

### 3.1 等待输出：先告诉模型任务还在运行

假设测试需要 40 秒，而某次工具调用只等待 10 秒输出：

```text
第 0 秒：启动测试。
第 10 秒：工具返回当前输出，并给出继续查询的会话标识。
第 10～40 秒：测试继续运行。
第 40 秒：测试结束，之后的查询取得最终结果。
```

这类似“先报告一下进度，稍后再来取结果”。统一执行器中的 `yield_time_ms` 用于这类等待；在可继续查询的执行路径中，等待期限到了可以返回仍在运行的会话。

### 3.2 执行超时：到点后安排终止

另一种规则是：“这次执行最多运行 60 秒。”如果走的是带执行超时的路径，到点后执行器会安排终止，而不只是返回进度。

Codex 的 `ExecExpiration` 表示超时或取消条件；超时计时使用现实经过时间。统一执行器也有等待执行完成的路径，会在完成期限耗尽、进程仍未退出时标记超时并调用终止逻辑。

因此，看见一个毫秒参数时，要先问：**它控制的是本次等待输出，还是这次执行的终止期限？**不能把某个执行分支的默认值推广成所有命令的统一寿命。

具体终止哪些进程，还涉及进程分组和清理范围，见 [[openai_codex_sandbox_processes|进程隔离与权限边界]]；设置了超时本身不能证明所有后代都已清理。

一手依据：[超时与取消条件](https://github.com/openai/codex/blob/091008729d5572712ac08964a9602eb71cf31428/codex-rs/core/src/exec.rs#L150)、[统一执行器的等待与超时处理](https://github.com/openai/codex/blob/091008729d5572712ac08964a9602eb71cf31428/codex-rs/core/src/unified_exec/process_manager.rs#L642)、[进程组终止路径](https://github.com/openai/codex/blob/091008729d5572712ac08964a9602eb71cf31428/codex-rs/core/src/exec.rs#L1027)。

## 4 输出限制：少存一些日志，不等于限制程序内存

假设图片程序不停打印进度。Codex 如果一直把全部日志存进自己的内存，执行器也可能被拖累，因此需要限制保存的输出量。

本次核对的统一执行器使用 `HeadTailBuffer`：输出过多时保留开头和最近的结尾，丢弃中间部分。相关缓冲的默认字节上限为 1 MiB，约 1024 KiB。

这个数字的对象是**特定输出缓冲**，并不是整个执行器或被执行程序的总内存上限。统一执行器还有不同用途的缓冲，不能把这一个常量当成所有输出占用的总和。

例如：

- 程序自己装载 2 GB 图片数据，即使只打印一行日志，也不受这项输出缓冲上限约束。
- 程序在项目目录写入一个很大的文件，即使终端不显示任何内容，也不会因为日志被截断而自动停止写文件。
- 工具返回内容的 token 上限，控制的是返回文本量，也不等于 CPU 或内存配额。

一手依据：[输出与管理数量常量](https://github.com/openai/codex/blob/091008729d5572712ac08964a9602eb71cf31428/codex-rs/core/src/unified_exec/mod.rs#L74)、[保留头尾的缓冲实现](https://github.com/openai/codex/blob/091008729d5572712ac08964a9602eb71cf31428/codex-rs/core/src/unified_exec/head_tail_buffer.rs#L5)、[不同用途的输出缓冲](https://github.com/openai/codex/blob/091008729d5572712ac08964a9602eb71cf31428/codex-rs/core/src/unified_exec/process.rs#L45)。

## 5 管理记录的数量上限，不等于子进程数量上限

本次源码中，统一执行器的 `MAX_UNIFIED_EXEC_PROCESSES` 为 64。管理器在需要时选择旧记录进行清理；源码还明确说明，在特定交互锁状态下，记录数量可能短暂超过软上限。

**软上限**可以理解成“尽量维持这个规模，特定情况下允许暂时超过”，不同于“第 65 个操作系统进程绝对无法创建”的硬限制。

这个 64 针对执行器管理的进程会话记录，不能理解为整棵进程树最多 64 个成员。例如，一个被管理的图片脚本启动 20 个助手，不代表管理器里必然新增 20 条同类会话记录。

所以需要分清：

| 限制 | 管的是什么 |
| --- | --- |
| 执行器管理记录的上限 | Harness 要维护多少个终端或执行会话 |
| 操作系统的任务数量配额 | 受限组里能创建多少进程、线程 |

一手依据：[64 的常量定义](https://github.com/openai/codex/blob/091008729d5572712ac08964a9602eb71cf31428/codex-rs/core/src/unified_exec/mod.rs#L77)、[管理记录的清理与软上限](https://github.com/openai/codex/blob/091008729d5572712ac08964a9602eb71cf31428/codex-rs/core/src/unified_exec/process_manager.rs#L1750)。

## 6 本地 Codex 实际确认了什么

在本次核对的本地命令执行、Linux 沙箱及相关执行器源码范围内，确认了超时或取消处理、有界输出缓冲、执行会话管理等机制；**未找到为每条本地命令统一建立 CPU、总内存及全部后代任务数量硬配额的实现**。

这个结论只针对上述版本与核对范围，不能扩展成“所有 Codex 产品和运行环境都没有资源配额”。命令可能运行在外层容器、虚拟机或管理员配置的控制组中，继承那一层的限制。要判断实际可用资源，还需要查看部署配置。

| 层次 | 要回答的问题 | 本次结论 |
| --- | --- | --- |
| 访问隔离 | 能读写哪里、能否联网、能否影响别的进程？ | 见 [[openai_codex_sandbox|沙箱总览]] 和进程专题 |
| Codex 执行管理 | 何时终止、保存多少输出、维护多少会话？ | 已核对上述执行护栏，分支和计数对象需区分 |
| 操作系统或外层环境配额 | 能用多少 CPU、内存、任务数量和磁盘？ | 需确认运行环境是否配置及具体数值 |

核对位置包括 `codex-rs/core/src`、`linux-sandbox/src`、`sandboxing/src`、`exec-server/src` 和 `utils/pty/src`；未发现统一硬配额实现不等于证明所有其他路径均无此能力。

## 7 用图片任务串起来理解

假设图片处理任务出现问题，可以按实际现象判断涉及哪层机制：

| 现象 | 应该怎样理解 |
| --- | --- |
| 想把结果写到禁止写入的目录，被拒绝 | 访问权限问题 |
| 一直计算，电脑变慢 | 关注 CPU 用量与实际配额，目录限制不能解决 |
| 图片太多，内存不够 | 关注程序用量和环境内存限制，日志截断不能解决 |
| 工具先返回“还在运行” | 可能只是本次等待输出结束，不等于已终止任务 |
| 执行到达明确的超时期限 | 执行器安排终止，后代清理范围需另行确认 |
| 日志中间被省略 | 可能是输出保留上限，不代表程序停止运行 |
| 允许写入的目录越来越大 | 关注磁盘配额或空间管理，写入权限不限制文件总量 |
